Stazione 01 · Dimensioni & iperparametri (B, T, C, V, H, hs)

Sei lettere che ricorrono ovunque

Tutto glassgpt.py è annotato con shape come (B, T, C): la misura di ogni dimensione di un tensore. Impararle qui rende leggibile ogni riga che segue — sono la segnaletica dell'intero modello.

Un tensore è un array n-dimensionale di numeri; la sua shape ne elenca le lunghezze. La convenzione del file è fissa: B è il batch (quante sequenze si processano insieme, in parallelo), T è la lunghezza di contesto (quanti token il modello guarda), C è la larghezza n_embd (quanti numeri descrivono ciascun token), V la dimensione del vocabolario, H il numero di attention head e hs = C/H la dimensione di un singolo head. Quindi un tensore (32, 64, 128) si legge: «32 sequenze, ognuna di 64 token, ogni token descritto da 128 numeri».

Attenzione a T. BLOCK_SIZE = 64 è il contesto massimo. Dentro forward la stessa lettera T indica la lunghezza corrente (≤ 64), che durante la generation cresce token dopo token fino a saturare la finestra.

Stazione 02 · BPE Tokenizer testo → id, fuori dalla rete, 0 parametri

Dal testo ai numeri: Byte-Pair Encoding

Una rete neurale opera su numeri. Il primo passo è quindi mappare il testo in token id interi — e il tokenizer di GlassGPT è un byte-level BPE costruito da zero nella classe BPETokenizer (righe 762–946).

L'idea in due mosse. 1) Si parte dai byte: qualunque testo, in qualunque lingua, in UTF-8 è una sequenza di byte 0…255. Il vocabolario base ha quindi 256 token e non esistono caratteri sconosciuti: un'emoji o una lettera rara sono semplicemente più byte (con un tokenizer char-level, un carattere mai visto in training rompeva l'encoding). Concretamente: «vita» = 4 byte (118, 105, 116, 97), mentre la «à» di «città» = 2 byte (195, 160) — l'UTF-8 spende più byte sui caratteri non-ASCII, e per il tokenizer va benissimo così. 2) Si impara a fondere le coppie più frequenti: si conta quali due token adiacenti compaiono più spesso (es. i+n) e li si fonde in un token nuovo (in, id 256). Si ripete: magari ora in+g → ing. Avanti così per BPE_VOCAB_SIZE − 256 = 256 merge, finché il vocabolario arriva a V = 512.

testo: c a m m i n c a m m i n a byte: [99][97][109][109][105][110] ... (0..255, vocab base) passo 1) conta le coppie adiacenti: (109,109)="mm" ×2 (97,109)="am" ×2 (99,97)="ca" ×2 ... passo 2) fondi la più frequente → "mm" diventa il nuovo id [256] c a [256] i n c a [256] i n a passo 3) ripeti: ora "ca" → [257], poi "[257]mm" → [258] ... [258] i n [258] i n a (i token si allungano)

Il risultato: i token diventano word piece ricorrenti, la stessa frase diventa una sequenza più corta di token, e nello stesso BLOCK_SIZE = 64 entra più contesto. Le fusioni apprese vengono registrate in merges come (id_a, id_b) → new_id; l'ordine di apprendimento è anche la priorità con cui si applicano in encode (il merge più vecchio, cioè con id più basso, vince sempre — esattamente come in training). vocab mappa invece ogni id ai byte che rappresenta: i primi 256 sono i byte stessi, dal 256 in poi le fusioni.

Tre dettagli fedeli al file. ① Garanzia di taglia: se il testo è troppo corto e i merge finiscono prima, train riempie i posti mancanti con token segnaposto b"" inerti, così vocab_size == 512 in ogni caso e la shape dell'embedding V×C non cambia mai. ② Costo: encode ricalcola _get_stats sull'intera sequenza a ogni merge → ~O(n·num_merge); un tokenizer di produzione usa strutture incrementali. ③ Merge oltre gli spazi: manca il pre-split in parole via regex, quindi il BPE può fondere token attraverso gli spazi (es. «del_» come token unico) — limite dichiarato nei commenti.

@staticmethod
def _get_stats(ids):
    """Count the frequency of every pair of CONSECUTIVE tokens in `ids`."""
    counts = {}
    for pair in zip(ids, ids[1:]):
        counts[pair] = counts.get(pair, 0) + 1
    return counts

@staticmethod
def _merge(ids, pair, new_id):
    """Replace every occurrence of `pair` with the single token `new_id`.
    Example: _merge([1, 2, 3, 1, 2], (1, 2), 99) -> [99, 3, 99]."""
    out, i = [], 0
    while i < len(ids):
        if i < len(ids) - 1 and ids[i] == pair[0] and ids[i + 1] == pair[1]:
            out.append(new_id); i += 2
        else:
            out.append(ids[i]); i += 1
    return out

def train(self, text, target_vocab_size, verbose=True):
    num_merges = target_vocab_size - 256
    ids = list(text.encode("utf-8"))     # text -> list of bytes (0..255)
    self._reset()
    for i in range(num_merges):
        stats = self._get_stats(ids)
        if not stats: break              # text too short: nothing left to merge
        pair = max(stats, key=stats.get) # the most frequent pair
        new_id = 256 + i
        ids = self._merge(ids, pair, new_id)
        self.merges[pair] = new_id
        self.vocab[new_id] = self.vocab[pair[0]] + self.vocab[pair[1]]
    for new_id in range(len(self.vocab), target_vocab_size):
        self.vocab[new_id] = b""         # inert placeholders: vocab_size is guaranteed

def encode(self, text):
    ids = list(text.encode("utf-8"))
    while len(ids) >= 2:
        stats = self._get_stats(ids)
        pair = min(stats, key=lambda p: self.merges.get(p, float("inf")))
        if pair not in self.merges: break
        ids = self._merge(ids, pair, self.merges[pair])
    return ids

def decode(self, ids):
    blob = b"".join(self.vocab[i] for i in ids)
    return blob.decode("utf-8", errors="replace")

def get_batch(split):
    d = train_data if split == "train" else val_data
    # Pick B random start positions. -BLOCK_SIZE so the window stays in bounds.
    ix = torch.randint(len(d) - BLOCK_SIZE, (BATCH_SIZE,))          # shape (B,)
    x = torch.stack([d[i : i + BLOCK_SIZE] for i in ix])            # shape (B, T)
    y = torch.stack([d[i + 1 : i + BLOCK_SIZE + 1] for i in ix])    # shape (B, T)
    return x.to(DEVICE), y.to(DEVICE)
Stazione 04 · Embeddings idx (B,T) → x (B,T,C)

Il COSA più il DOVE: nasce il residual stream

Un token id è un intero che non porta alcuna informazione sul token. L'embedding mappa ogni id in un vettore appreso di C = 128 numeri reali: partono casuali, e il training li aggiusta così che token usati in contesti simili ottengano vettori simili.

Servono due tabelle. token_embedding (V, C) = (512, 128) è una lookup table: dato l'id, restituisce la sua riga — il COSA (contenuto del token). position_embedding (T, C) = (64, 128) codifica invece il DOVE: la self-attention è permutation-invariant — senza informazione di posizione «abc» e «cba» produrrebbero la stessa rappresentazione — quindi a ogni token si somma un vettore appreso che codifica il suo indice 0, 1, 2…

x = token_embedding[idx] + position_embedding[0..T−1] → (B, T, C)

La somma sfrutta il broadcasting: pos_emb ha shape (T, C) e si "allarga" automaticamente su tutte le B sequenze del batch — ogni sequenza usa le stesse posizioni 0…T−1. Nota fedele al codice: pos = torch.arange(T, device=idx.device) prende il device dagli input, non dalla costante globale, così il modello gira ovunque girino i suoi dati. Il tensore risultante x (B, T, C) è il residual stream: il "nastro trasportatore" a cui ogni Block della stazione 08 aggiungerà i propri contributi senza mai sostituirlo.

Che cosa significano, quei numeri

All'inizio non significano niente: partono casuali e l'addestramento decide. Ma la disposizione su cui l'addestramento converge spiega buona parte dell'architettura che viene dopo.

Le direzioni portano significato. Nello spazio su cui l'addestramento converge, le direzioni corrispondono a proprietà: la differenza fra due vettori imparentati, sommata a un terzo, cade vicino a un quarto:

embedding("re") − embedding("uomo") + embedding("donna") ≈ embedding("regina")

Il passo da «uomo» a «donna» è lo stesso che porta da «re» a «regina»: una direzione dello spazio ha finito per codificare qualcosa come il genere. Vale anche per il numero — embedding("gatti") − embedding("gatto") è una direzione «più di uno», e il suo prodotto scalare con altri sostantivi risulta sistematicamente più alto per i plurali. Gli embedding veri approssimano soltanto queste identità, perché «regina» non è solo «re al femminile», ma il principio regge: il significato vive nelle direzioni, e uno spazio con molte dimensioni ha posto per molte direzioni indipendenti.

Il prodotto scalare misura l'allineamento. È l'operazione su cui è costruito tutto il resto: positivo quando due vettori puntano dalla stessa parte, zero quando sono perpendicolari, negativo quando sono opposti. Ogni prodotto fra matrici in questo file è una pila di prodotti scalari, e la domanda è sempre la stessa — quanto sono allineati questi due? Vale per Q · Kᵀ nell'attention, per le righe dell'up-projection nell'MLP e per lm_head, dove il prodotto scalare fra x e l'embedding del token v è esattamente il logit di v.

Il vettore assorbe il contesto. La tabella degli embedding è una lookup e non sa niente di ciò che le sta intorno: il vettore di «piano» è identico in «il piano di sopra», «suona il piano» e «il piano è fallito» — una riga di tabella, tre significati scollegati. Tutto quello che viene dopo serve a rimediare. Ogni Block somma al vettore che riceve, così il significato si accumula strato dopo strato: è per questo che l'ultima posizione, l'unica che la generazione legge, può arrivare a contenere tutto il contesto rilevante.

Stazione 05 · Un Head di self-attention x (B,T,C) → out (B,T,hs)

Query, Key, Value: chi guarda chi

Per predire il prossimo token, alcune posizioni del contesto contano più di altre: in «…the runnin_» la desinenza «g» dipende da «runnin», non da «the». Un head impara, per ogni posizione, quali posizioni precedenti pesare — è il meccanismo con cui l'informazione si mescola tra i token.

Ogni vettore-token viene proiettato linearmente (tre nn.Linear(C, hs, bias=False), senza bias) in tre viste da hs = 32 numeri: la Query (Q) — ciò che il token cerca, confrontata con le Key altrui; la Key (K) — ciò che il token offre, confrontata con le Query altrui; il Value (V) — il contenuto che viene aggregato quando il token riceve attenzione. L'output del token i è la somma pesata dei Value dei token j, con pesi dati da:

outi = Σj≤i softmaxj( Qi · Kj / √hs ) · Vj

Una domanda, una risposta, una correzione. Ogni vettore-token viene moltiplicato per tre matrici distinte, e ne escono tre vettori con tre ruoli diversi. Sulla frase «la soffice creatura blu», il sostantivo «creatura» emette una Query che vale più o meno ci sono aggettivi qui intorno?; «soffice» e «blu» emettono Key che si allineano con quella domanda; e il Value di «soffice» è ciò che trasforma una creatura generica in una creatura soffice. Il confronto avviene sempre fra token diversi: la Query di «creatura» viene messa a prodotto scalare con la Key di ciascun token che la precede, una coppia alla volta. Un prodotto scalare grande significa che quella Key risponde a quella Query, ed è il primo calcolo che il head esegue.

Il Value è una correzione. Il vettore Value viene sommato al residual stream: l'attention propone aggiustamenti a quello che il token già porta con sé. E l'esempio aggettivo-sostantivo resta una finzione comoda: i pesi di un head vero fanno qualunque cosa riduca la loss, e di solito un head solo porta avanti più compiti scollegati insieme.

Tre aggettivi definiscono il meccanismo. Self: Q, K e V vengono tutti dalla stessa sequenza. Causale: un token guarda solo posizioni ≤ della propria — il futuro è mascherato, perché contiene proprio i token da predire. Scalata: la divisione per √hs impedisce ai dot product di crescere con hs; senza, la softmax saturerebbe (uscite ≈ 0 o 1) e i gradienti svanirebbero. La maschera è una matrice triangolare inferiore (tril): dove vale 0 si scrive −∞, che la softmax trasforma in peso esattamente 0.

chi viene guardato → t0 t1 t2 t3 t0 [ ok | -inf | -inf | -inf ] guarda t1 [ ok | ok | -inf | -inf ] -inf → 0 dopo la softmax ↓ t2 [ ok | ok | ok | -inf ] t3 [ ok | ok | ok | ok ]

Nel codice: wei = q @ k.transpose(−2,−1) * hs−0.5 produce (B, T, T) affinità; masked_fill(tril==0, −inf) applica la causalità; softmax(dim=−1) normalizza ogni riga a somma 1; un dropout agisce sui pesi in training; infine out = wei @ v restituisce (B, T, hs). La tril non vive nell'head: è definita una sola volta in MultiHeadAttention e passata a tutti gli head (stazione 06).

Perché lo scaling: satura la softmax

Moltiplica gli score della riga selezionata: più crescono in modulo, più la softmax si concentra su un solo token (≈ one-hot) e il gradiente verso gli altri svanisce. La divisione per √hs tiene i punteggi in una zona "morbida".

def forward(self, x, tril):
    # x:    (B, T, C). B sequences, T tokens, C numbers per token.
    # tril: (T, T) lower-triangular of ones = the causal mask.
    B, T, C = x.shape
    k = self.key(x)      # (B, T, hs) - the KEY projection
    q = self.query(x)    # (B, T, hs) - the QUERY projection

    # Attention scores: dot product between every Query and every Key.
    # (B, T, hs) @ (B, hs, T) = (B, T, T). Divided by sqrt(hs): without it,
    # large hs makes the dot products large, the softmax saturates
    # (outputs near 0 or 1), and the gradients vanish.
    wei = q @ k.transpose(-2, -1) * (HEAD_SIZE**-0.5)     # (B, T, T)

    # Causal mask: where tril==0 (future tokens) put -infinity, so after
    # the softmax those weights become 0. Token i never attends to j>i.
    wei = wei.masked_fill(tril == 0, float("-inf"))       # (B, T, T)

    wei = F.softmax(wei, dim=-1)                          # (B, T, T)
    wei = self.dropout(wei)

    # Aggregation: Value vectors averaged with the attention weights.
    v = self.value(x)    # (B, T, hs) - the VALUE projection
    out = wei @ v        # (B,T,T) @ (B,T,hs) = (B, T, hs)
    return out
Stazione 06 · Multi-Head Attention H×(B,T,hs) → concat → (B,T,C)

Quattro sguardi in parallelo

Un solo head impara una relazione tra posizioni. GlassGPT ne fa girare H = 4 in parallelo, ciascuno con le proprie proiezioni Q/K/V su hs = 32 dimensioni: ogni head può specializzarsi in una relazione diversa (sintassi vicina, rime lontane, ripetizioni…).

x (B,T,128) --+--> Head 1 --> (B,T,32) --+ +--> Head 2 --> (B,T,32) --+ concat proj (128→128) +--> Head 3 --> (B,T,32) --+--> (B,T,128) ---> (B,T,128) +--> Head 4 --> (B,T,32) --+ | | | Q/K/V indipendenti 4×32 = 128 mescola tra per ogni head (torna a C) gli head

I quattro output (B, T, 32) vengono concatenati lungo l'ultima dimensione (torch.cat(..., dim=−1)): 4×32 = 128 = C, si torna alla larghezza del residual stream. Segue una proiezione finale proj: Linear(C, C) che mescola le informazioni tra gli head (fin qui ognuno lavorava nel suo sottospazio isolato).

Che cosa si guadagna, visto che il costo è identico

Quattro head da 32 costano esattamente quanto un head solo da 128: 3 × 4 × 128 × 32 = 3 × 128 × 128 = 49 152 parametri in entrambi i casi. Il guadagno sta quindi altrove: ogni head esegue la propria softmax. Una posizione può così attendere all'aggettivo che ha a sinistra e al soggetto dieci token indietro nello stesso passaggio. Un head largo ha una sola distribuzione di attenzione da spendere, e dividerla fra due bersagli significa rinunciare a entrambi.

Perché la mappa dei Value è spezzata in due

La correzione prodotta da un head deve atterrare nel residual stream, che ha C dimensioni: sulla carta la mappa dei Value va quindi da C a C. Scritta così costerebbe 128 × 128 = 16 384 parametri per head, contro i 4 096 di Query e di Key — una mappa che domina le altre due, con lo squilibrio che peggiora a ogni head aggiunto.

Per questo la si fa passare da una strozzatura. Head.value si occupa della discesa, C → hs; la risalita hs → C vive in un'unica matrice condivisa da tutto il blocco, proj, dove le quattro risalite stanno affiancate. I 32 slot del concat che appartengono a un head vengono toccati solo dalla propria fetta 128 × 32 della matrice, e i conti tornano esatti: 128 × 128 = 4 × (32 × 128), cioè 4 096 per head. La mappa dei Value completa di un head costa quindi 4 096 in discesa più 4 096 in risalita — quanto la sua Query e quanto la sua Key.

Che cosa comporta la strozzatura. La mappa dei Value di ogni head resta vincolata a rango hs: ogni correzione che può produrre deve passare per 32 dimensioni, ed è una restrizione voluta. Da qui nasce anche una confusione di nomi: nei paper «la matrice dei Value» indica di solito solo la parte in discesa (C → hs), mentre la risalita viene descritta a parte come proiezione d'uscita del blocco, W_O. Sono la stessa cosa vista in due pezzi.
Due dettagli del file. ① proj è marcata IS_RESIDUAL_PROJ = True: scrive nel residual stream, quindi in _init_weights riceverà la init ridotta 0.02/√(2·N_LAYER) (stazione 09). ② La causal mask è registrata qui una volta sola con register_buffer("tril", torch.tril(torch.ones(T,T))): fa parte del modello (segue .to(device), finisce nel checkpoint) ma non è un parametro allenabile; in forward viene affettata alla lunghezza corrente (self.tril[:T,:T], perché in generation T cresce) e passata identica a tutti gli head — un buffer solo invece di H·N_LAYER copie.

def __init__(self):
    super().__init__()
    self.heads = nn.ModuleList([Head() for _ in range(N_HEAD)])
    # Final projection applied after concatenating the heads. H*hs = C.
    self.proj = nn.Linear(N_EMBD, N_EMBD)
    self.proj.IS_RESIDUAL_PROJ = True   # -> scaled init (see GPT._init_weights)
    self.dropout = nn.Dropout(DROPOUT)
    # THE single copy of the causal mask, shared by all heads in this layer.
    # register_buffer: part of the model (moves with .to(device), saved in the
    # checkpoint) but NOT a trainable parameter.
    self.register_buffer("tril", torch.tril(torch.ones(BLOCK_SIZE, BLOCK_SIZE)))

def forward(self, x):
    # Slice the mask to the current length T (in generation T grows).
    T = x.shape[1]
    tril = self.tril[:T, :T]                              # (T, T)
    # Run the H heads and concatenate along the last dim:
    # H times (B, T, hs) -> (B, T, H*hs) = (B, T, C)
    out = torch.cat([h(x, tril) for h in self.heads], dim=-1)   # (B, T, C)
    out = self.dropout(self.proj(out))                    # (B, T, C)
    return out
Stazione 07 · FeedForward (MLP) (B,T,C) → (B,T,4C) → (B,T,C)

Espandi, filtra, ricomprimi — un token alla volta

L'attention mescola informazione tra le posizioni; il FeedForward la elabora posizione per posizione, applicando gli stessi pesi a ogni token in modo indipendente. Nei modelli grandi è qui che vive la maggioranza dei parametri.

(B,T,128) —Linear→ (B,T,512) —ReLU→ (B,T,512) —Linear→ (B,T,128)

La prima Linear(C, 4C) espande ×4: uno spazio nascosto più largo (512) dà al layer più capacità di calcolo. La ReLU azzera i valori negativi: è la non-linearità, e senza di essa due Linear consecutive collasserebbero in un'unica mappa lineare — la rete non potrebbe apprendere funzioni non lineari. La seconda Linear(4C, C) ricomprime a C per rientrare nel residual stream; è definita a parte nel codice proprio per marcarla IS_RESIDUAL_PROJ (init ridotta). Chiude un Dropout(0.1), attivo solo in training.

Che cosa fanno davvero le due matrici

L'attention sposta informazione fra le posizioni. Questo blocco lascia ogni posizione per conto suo — e allora a cosa servono i due terzi della rete? La risposta più accreditata è che qui stanno i fatti, e che le due matrici hanno ruoli opposti: la prima fa domande, la seconda scrive risposte.

L'up-projection va letta per righe. Ognuna delle sue 4C righe è un vettore nello stesso spazio di x, quindi il prodotto scalare di una riga con x chiede: quanto questo token punta nella direzione di quella riga? Si supponga che una riga contenga la direzione (nome «Michael») + (cognome «Jordan»). Ogni metà che corrisponde contribuisce circa 1 al prodotto scalare, quindi quella riga produce 2 se x codifica il nome completo, 1 se ne codifica solo metà (un «Michael Phelps» qualsiasi), 0 o meno se nessuno dei due.

Il bias aggiunge una soglia: con −1 in quella posizione l'uscita della riga vale 1 per il nome completo, 0 per una metà sola, negativa quando non corrisponde nulla. La ReLU poi azzera tutto ciò che è negativo, e quel che esce è un sì/no netto — diverso da zero per «Michael Jordan», zero tondo per «Michael Phelps» o «Alexis Jordan». Senza, il layer lascerebbe passare credito parziale per una mezza corrispondenza. Soglia più taglio si comportano insieme come una porta AND.

I valori che escono dalla ReLU sono quelli che si chiamano neuroni del transformer: 4C per token, detti attivi quando sono positivi.

La down-projection va letta per colonne. Ognuna delle 4C colonne è anch'essa un vettore nello spazio di x, e l'uscita è la somma di quelle colonne, ciascuna scalata dal proprio neurone. Una colonna è dunque ciò che viene aggiunto al token quando il suo neurone si accende. Se la colonna abbinata al neurone «Michael Jordan» contiene la direzione «basketball», il blocco ha immagazzinato un fatto: entra un vettore che codifica quel nome, esce con «basketball» sommato.

riga · x → neurone · colonna → sommato allo stream
«è questo X?» «allora aggiungi Y»
Superposizione: perché i neuroni non si leggono uno per uno. Guardando dentro un modello addestrato non si trova quasi mai un «neurone Michael Jordan»: le feature stanno sparse su molti neuroni insieme, e c'è un motivo. Feature disposte lungo direzioni esattamente perpendicolari non si disturbano a vicenda, e uno spazio a C dimensioni ne contiene esattamente C: sistemate così, le feature possono essere al massimo C. Basta però allentare il requisito a «quasi perpendicolari», ad esempio 85° invece di 90°, e il numero di direzioni disponibili cresce esponenzialmente con C (conseguenza del lemma di Johnson-Lindenstrauss): alle 12 288 dimensioni di GPT-3 sono decine di miliardi. Conviene quindi impacchettare molte più feature che dimensioni, accettando un po' di interferenza — al prezzo della leggibilità: una feature finisce per essere un disegno distribuito su molti neuroni. Con i C = 128 di questo file lo spazio per tutto ciò è minimo: il meccanismo gira lo stesso, su uno spazio troppo piccolo perché renda.

Stazione 08 · Block: pre-norm + residual x = x + sublayer(LayerNorm(x))

Il pattern che rende possibile la profondità

Un Block = attention (mescola tra posizioni) + MLP (trasforma per posizione). GlassGPT ne impila 4; i modelli grandi, decine. Due meccanismi rendono ottimizzabile la pila — e sono presenti in ogni Transformer.

x ----------------------------(+)------------------------------(+)----> x | ^ ^ | l'input viene sommato \ identity path, di nuovo \ | inalterato \ \ +--> LayerNorm --> Multi-Head ---+ +--> LayerNorm --> FeedFwd ---+ (mescola posizioni) (per posizione) x = x + MultiHeadAttention(LayerNorm(x)) # riga 1430 x = x + FeedForward(LayerNorm(x)) # riga 1431

1) Residual connection. L'output del sublayer viene sommato all'input (x = x + sublayer(x)), mai sostituito. Esiste così un cammino identità lungo cui attivazioni e — soprattutto — gradiente fluiscono intatti attraverso la profondità: nel backward, la derivata di x + f(x) contiene sempre un termine 1. Senza residual, reti profonde diventano difficilissime da ottimizzare (il segnale si attenua moltiplicativamente strato dopo strato).

2) LayerNorm, in pre-norm. Normalizza ogni token a media 0 e varianza 1 lungo i suoi C canali, poi applica scala γ e traslazione β apprese: attivazioni di magnitudine limitata, training stabile. «Pre-norm» = si normalizza prima del sublayer (dentro la parentesi), non dopo: il ramo identità resta davvero pulito.

LayerNorm(x)c = γc · ( xc − μ ) / √(σ² + ε) + βc con μ, σ² calcolate sui C canali del token

L'altra condizione della profondità: dove entra la non-linearità

Una pila di prodotti fra matrici resta un prodotto fra matrici: W1·(W2·(W3·x)) collassa in (W1·W2·W3)·x. Senza qualcosa di non lineare in mezzo, tutti e quattro i Block si ridurrebbero algebricamente a una sola mappa lineare e la profondità non comprerebbe nulla. Nel file la linearità si rompe in cinque punti:

  1. La ReLU nell'MLP, la sorgente principale. Nei modelli moderni al suo posto c'è SwiGLU o GeLU, ma il ruolo è identico.
  2. La softmax dell'attention, che normalizza ogni riga.
  3. Q · Kᵀ è quadratico nell'input: x compare due volte, una attraverso WQ e una attraverso WK, quindi i punteggi sono già non lineari prima della softmax.
  4. Il LayerNorm, che divide per la deviazione standard del vettore stesso.
  5. La softmax più il campionamento in uscita.
Il terzo punto è quello che sfugge. L'attention viene spesso descritta come «lineare, dati i pesi», ed è vero: fissata A = softmax(…), il passo A·V è un'operazione lineare. Ma A viene calcolata a partire da x: ogni input si costruisce la propria matrice di mescolamento strada facendo.

class Block(nn.Module):
    def __init__(self):
        super().__init__()
        self.sa = MultiHeadAttention()   # self-attention: mix across positions
        self.ffwd = FeedForward()        # MLP: per-position transform
        self.ln1 = nn.LayerNorm(N_EMBD)  # normalize before attention
        self.ln2 = nn.LayerNorm(N_EMBD)  # normalize before the MLP

    def forward(self, x):
        x = x + self.sa(self.ln1(x))     # residual around attention
        x = x + self.ffwd(self.ln2(x))   # residual around the MLP
        return x
Stazione 08 · Il residual stream, passo per passo read → transform → write (+)

Segui il tensore x, una scrittura alla volta

Lo stream è la memoria di lavoro del modello: un unico tensore (B, T, C) che scorre dall'inizio alla fine. Nessun layer lo sovrascrive — ognuno ne legge una copia normalizzata, calcola un contributo Δ della stessa shape e lo riversa dentro con una somma.

La stazione 08 ha spiegato perché il pattern x = x + sublayer(LayerNorm(x)) funziona; qui lo si percorre read → transform → write, un nodo alla volta. Premi avanti e osserva chi legge, chi produce un Δ e chi lo somma alla banda.

La contabilità dello stream. Alla fine x = embeddings + Δ₁ + Δ₂ + … + Δ₈: otto contributi sommati, mai sostituiti. È il motivo per cui l'init delle proiezioni residuali è smorzata di 1/√8 (stazione 09) — la varianza di una somma cresce col numero di addendi — ed è il motivo per cui il gradiente arriva pulito fino al primo layer: nel backward la derivata «attraversa» ogni + senza ostacoli.
Stazione 09 · Il modello GPT completo idx (B,T) → logits (B,T,V)

Assemblaggio, weight tying, inizializzazione

La classe GPT monta tutto: le due tabelle di embedding, i 4 Block in nn.Sequential, un LayerNorm finale (ln_f) e la testa lm_head: Linear(C, V) che proietta ogni vettore da 128 numeri a 512 logit — un punteggio per ogni token del vocabolario come "prossimo token", a ogni posizione.

Weight tying. La tabella di embedding (V, C) e la matrice della testa finale (V, C) hanno la stessa forma e rappresentano la stessa relazione token↔vettore, in direzioni opposte («id → vettore» e «vettore → punteggio per id»). Il file le lega: self.lm_head.weight = self.token_embedding.weight — lo stesso identico tensore, riusato. Benefici: ~V·C = 65 536 parametri in meno e spesso migliore generalizzazione; da quel momento aggiornare l'una aggiorna l'altra. Solo la matrice è condivisa: il bias di lm_head resta un parametro separato (V = 512 numeri).

L'ordine conta (un bug silenzioso evitato). Prima si inizializza tutto con self.apply(_init_weights), poi si lega. Legando prima, apply() inizializzerebbe lo stesso tensore due volte (come Embedding e come Linear): oggi innocuo perché le due std coincidono, ma un bug latente il giorno in cui divergessero. Il commento del file lo dichiara esplicitamente (righe 1486–1490).

Inizializzazione. Tutti i pesi partono Normal(0, 0.02) (bias a zero): piccoli, per attivazioni limitate all'avvio. Ma le proiezioni marcate IS_RESIDUAL_PROJ — quelle che scrivono nel residual stream: la proj dell'attention e la seconda Linear dell'MLP — usano una std ridotta: 0.02/√(2·N_LAYER) = 0.02/√8 ≈ 0.00707. Il motivo: a ogni layer si sommano due contributi al flusso (attention + MLP), cioè 2·N_LAYER = 8 somme totali; senza smorzamento la varianza del segnale crescerebbe layer dopo layer. Il fattore 1/√(2·N_LAYER) compensa esattamente quella somma cumulativa.

Stazione 10 · Loss: cross-entropy logits (B·T, V) + targets (B·T) → scalare

Quanto sbaglia il modello, in un numero

I logit sono punteggi grezzi: più alto il logit, più alta la probabilità che il modello assegna a quel token come "prossimo". La cross-entropy è bassa quando il modello dà probabilità alta al token giusto (quello in targets), alta quando sbaglia — ed è la quantità che il training minimizza.

p = softmax(logits) ; loss = −log p[target]

F.cross_entropy vuole logits (N, V) e target (N,), quindi il forward appiattisce insieme le dimensioni B e T: logits.view(B·T, V), targets.view(B·T) — con B=32 e T=64 sono 2 048 predizioni valutate per batch, e la loss è la loro media. Un check di sanità prezioso: a pesi casuali il modello predice ~uniforme su V token, e la cross-entropy dell'uniforme su N opzioni è esattamente ln(N). Con V = 512: ln(512) ≈ 6.2383. Se la loss parte lì vicino, l'inizializzazione è corretta.

Quattro righe che fanno imparare 866 048 pesi

Il ciclo di train_model ripete MAX_ITERS = 2000 volte la stessa danza: pesca un batch, misura l'errore, calcola come muovere ogni peso, muovilo. Tutto il resto del file esiste per rendere possibili queste quattro righe.

get_batch("train") 1) pesca x, y (B,T) | v FORWARD: model(x, y) ------> 2) loss (l'errore di predizione) | | | zero_grad() (azzera i vecchi gradienti!) | | | 3) BACKWARD: loss.backward() d(loss)/d(peso) | | | 4) UPDATE: optimizer.step() aggiorna i pesi +--------------------------+ ripeti MAX_ITERS volte

Backward. loss.backward() è l'autograd di PyTorch: per ognuno dei ~866 048 pesi calcola la derivata della loss rispetto a quel peso — quanto e in che verso muoverlo per ridurre l'errore. Zero_grad prima: PyTorch accumula i gradienti, quindi senza optimizer.zero_grad(set_to_none=True) ogni step sommerebbe i gradienti dello step precedente ai propri. Update. AdamW adatta il passo per ciascun parametro usando medie mobili del gradiente e del suo quadrato — l'ottimizzatore standard per i Transformer, qui con lr = 3e-4.

AdamW · per ogni peso (g = gradiente)
m ← β₁·m + (1−β₁)·g · v ← β₂·v + (1−β₂)·g² · θ ← θ − lr·( m̂ /(√v̂+ε) + λ·θ )

m è la media mobile del gradiente (il momento), v quella del suo quadrato: insieme danno a ogni parametro un passo su misura — ampio dove il gradiente è coerente, ridotto dove è rumoroso (m̂ e v̂ sono le versioni corrette dal bias dei primi step). Il termine λ·θ è il decoupled weight decay, la «W» di AdamW: spinge i pesi verso valori piccoli, cioè funzioni più semplici e meno overfitting.

Stazione 12 · Generation: sampling temperature → top-k → softmax → multinomial

Un token alla volta, in autoregressione

Generare = ripetere il forward in un loop autoregressivo: ogni token campionato viene appeso al contesto e ridato in pasto al modello per predire il successivo. @torch.no_grad() spegne l'autograd: in generation i gradienti non servono.

contesto idx (B, t) | ritaglia agli ultimi BLOCK_SIZE token idx[:, -BLOCK_SIZE:] v forward → logits, prendi SOLO l'ultima posizione (B, V) | / temperature (scala i logit) | top-k (tieni i K più probabili, resto → -inf) | softmax (→ probabilità) | multinomial (campiona 1 token: NON sempre il massimo) v idx_next (B,1) ──► append: idx = [idx, idx_next] (B, t+1) | | +───────────────────────────────────+ ripeti MAX_NEW_TOKENS volte

Temperature divide i logit prima della softmax: τ < 1 affila la distribuzione concentrando la probabilità sui token più probabili (output più ripetitivo); τ = 1 la lascia intatta; τ > 1 la appiattisce (output più vario, più code campionate). Una guardia max(temperature, 1e-6) evita la divisione per zero. Top-k trova il K-esimo logit più alto con torch.topk(...).values[:, [-1]] e manda a −∞ tutto ciò che sta sotto: dopo la softmax quei token hanno probabilità esattamente 0 — via la coda di token improbabili ma non impossibili. Infine torch.multinomial campiona dalla distribuzione invece di prendere l'argmax: è questa casualità controllata a dare varietà al testo. I default del file: τ = 0.8, K = 50, 500 token generati.

@torch.no_grad()  # generation needs no gradients -> faster/lighter
def generate(self, idx, max_new_tokens, temperature=1.0, top_k=None):
    temperature = max(temperature, 1e-6)     # avoid division by zero
    for _ in range(max_new_tokens):
        # The model attends to at most BLOCK_SIZE tokens: crop the context.
        idx_cond = idx[:, -BLOCK_SIZE:]      # (B, <=T)
        logits, _ = self(idx_cond)           # (B, T, V)
        # Only the LAST position matters; divide by the temperature.
        logits = logits[:, -1, :] / temperature          # (B, V)
        # top-k: keep only the K highest logits; the rest -> -infinity.
        if top_k is not None:
            k = min(top_k, logits.size(-1))
            threshold = torch.topk(logits, k).values[:, [-1]]   # (B, 1)
            logits = logits.masked_fill(logits < threshold, float("-inf"))
        probs = F.softmax(logits, dim=-1)                # (B, V)
        # Sample from the distribution instead of taking the argmax.
        idx_next = torch.multinomial(probs, num_samples=1)      # (B, 1)
        idx = torch.cat((idx, idx_next), dim=1)          # (B, T+1)
    return idx
Stazione 12 · Inferenza: prefill e decode lo stesso grafo, due forme diverse

Perché generare costa in modo così diverso da addestrare

L'addestramento fa un forward per batch. La generazione ne fa uno per token, e quei forward hanno due forme. Il primo legge tutto il prompt in una volta; ognuno dei successivi legge un token solo, quello appena prodotto. I sistemi di serving chiamano le due fasi prefill e decode: stesso codice, colli di bottiglia opposti. GlassGPT implementa la versione semplice; la separazione spiega quasi tutto di come si comportano gli LLM in produzione.

Con un prompt da 1000 token e 200 token generati, lo stesso identico grafo di calcolo viene eseguito 201 volte:

PREFILL 1 forward, 1000 token in un colpo solo, una volta sola |###################################| → TTFT (time to first token: l'attesa prima che compaia del testo) DECODE 200 forward, 1 token ciascuno, rigorosamente in fila |#|#|#|#|#|#|#|#|#|#|#|#|#|#|#|#|#|#| … → TPOT il token n è l'input del token n+1: non si parallelizza (time per output token: la velocità con cui scorre il testo)
PREFILL — matrice × matrice (GEMM), limitato dal calcolo
X [1000 × C] tutte le posizioni insieme A [1000 × 1000] O(n²), metà mascherata KV cache 1000 righe scritte logits serve solo l'ultima riga

Le altre 999 righe di logits vengono buttate: quel forward serviva a riempire la cache, non a predire. La GPU lavora vicino al picco di FLOPs, quindi aggiungere richieste al batch non porta nulla — è già satura.

DECODE — vettore × matrice (GEMV), limitato dalla memoria
x [1 × C] un solo token A [1 × 1000] O(n), una riga sola KV cache letta tutta, +1 riga logits usati per intero

L'aritmetica è minuscola, ma per produrre quel token servono comunque tutti i pesi letti dalla memoria: 140 GB per un modello grande. La GPU resta quasi ferma ad aspettare. Qui il batching paga moltissimo — la stessa lettura dei pesi serve 32 richieste insieme.

Decodifica speculativa: spendere il calcolo che avanza

Il decode spreca quasi tutta la capacità aritmetica: i pesi vanno letti per intero per produrre un token solo, e mentre vengono letti le unità di calcolo non hanno niente da fare. L'asimmetria che ne segue è tutta l'idea: verificare 4 token costa quasi quanto generarne 1, perché in un caso e nell'altro i pesi si caricano una volta.

Un secondo modello, molto più piccolo — il draft — tira a indovinare in avanti, e il modello vero — il target — controlla le proposte in un passaggio unico:

draft (piccolo, veloce) propone 4 token: " and" / " then" / " he" / " ran" | target (il modello vero) UN forward su tutti e 4 insieme (forma da prefill: GEMM, non GEMV) | confronta ogni proposta con quello che avrebbe prodotto da solo | accettati: " and then he" <---+ i primi tre combaciano, il quarto no: viene scartato e sostituito dal token del target | risultato: 4 token emessi al costo di circa 1 forward del target
Non è un'approssimazione. Con la regola di accettazione giusta — un passo di rejection sampling che corregge la differenza fra le due distribuzioni — il testo prodotto è campionato esattamente dalla distribuzione che avrebbe prodotto il target da solo. Il draft cambia soltanto la velocità con cui i token arrivano: se è scadente viene respinto più spesso e il guadagno scende verso 1×. Ogni passo emette almeno un token, quello del target, quindi si avanza anche quando tutte le proposte sbagliano. I guadagni tipici stanno fra 2× e 3×, governati dal tasso di accettazione — cioè da quanto spesso un modello economico si trova d'accordo con uno costoso. Capita spesso, perché buona parte di qualsiasi testo è facile: spazi, parole di servizio, la seconda metà di una parola già cominciata.

Le varianti cambiano soprattutto da dove arriva il draft: un modello piccolo della stessa famiglia, una ricerca n-gram nel prompt (nessun modello, si propone testo copiato dal contesto — funziona bene su riassunti e modifiche di codice), oppure teste di predizione aggiuntive innestate sul target stesso, come in Medusa ed EAGLE, che evitano di servire due modelli.

Che cosa fa invece questo file

GPT.generate non ha KV cache: a ogni passo rifà il forward completo su tutto il contesto, quindi K e V dei token precedenti vengono ricalcolati da zero ogni volta. Corretto, molto più leggibile — e O(T) volte il lavoro necessario. Ogni passo è, di fatto, un piccolo prefill: la forma che un servizio reale paga una volta sola.

Perché aggiungere la cache non sarebbe solo una questione di velocità. Questo modello usa posizioni assolute apprese, sommate una volta all'ingresso. Quando il contesto supera BLOCK_SIZE la finestra scorre, l'indice di posizione di ogni token cambia, e i K/V in cache — che hanno le vecchie posizioni già cotte dentro — diventano sbagliati: la cache andrebbe ricostruita. RoPE non ha questo problema, perché applica la posizione ruotando Q e K dentro ogni attention, in base alla distanza relativa. È buona parte del motivo per cui i modelli moderni ci sono passati.
Sulla scala. Il discorso sui colli di bottiglia riguarda GPU che spostano decine di gigabyte di pesi. GlassGPT ha 866 048 parametri e gira su CPU: niente di tutto ciò è osservabile qui. È documentato perché l'architettura è la stessa.
